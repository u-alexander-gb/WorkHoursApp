# Модель данных

Приложение хранит данные локально в SQLite. Android и Windows используют одну структуру базы. Идентификаторы генерируются на устройстве, поэтому резервную копию можно перенести на другое устройство.

## Текущая схема: версия 4

### `projects`

`id`, `name`, `archived`, `track_pay`. По умолчанию `track_pay = 0`: проект учитывает только часы. При `track_pay = 1` можно выбрать один из его тарифов. Существующие проекты из старой базы и старые резервные копии мигрируют с `track_pay = 1`, чтобы не менять прежнее поведение.

### `rates`

`id`, `project_id`, `name`, `cents_per_hour`, `currency`, `archived`. Сумма хранится в центах за час. Смена сохраняет снимок выбранной ставки, чтобы прежний расчёт не менялся при будущей правке тарифа.

### `shifts`

`id`, `row_number`, `project_id`, `rate_id`, `status`, `planned_start_ms`, `planned_end_ms`, `pre_check_in_ms`, `confirmed_ms`, `credited_start_ms`, `checked_out_ms`, `credited_end_ms`, `break_minutes`, `rate_name_snapshot`, `rate_cents_snapshot`, `currency_snapshot`. `row_number` — постоянный порядковый Row ID, который включается в CSV и не переиспользуется после удаления плана. У смены без оплаты `rate_id` и поля снимка тарифа равны `NULL`; часы всё равно рассчитываются.

Состояния: `planned`, `active`, `completed`, `cancelled`. Старый статус `armed` принимается при миграции и восстановлении копии, затем переводится в `active`. Поля времени содержат миллисекунды с Unix epoch. Время нажатия check-in (`pre_check_in_ms`) и check-out записывается отдельно от времени, по которому считаются часы. Поле `confirmed_ms` сохраняется для прежних записей.

### `shift_events`

`id`, `shift_id`, `kind`, `recorded_ms`, `credited_ms`, `details_json`. События планирования, check-in, удаления из расписания и check-out сохраняются как исходные отметки. Исправление добавляет новое событие `corrected`; в `details_json` находятся причина и значения `before`/`after`. Прежние события не переписываются.

### `project_events`

`id`, `project_id`, `recorded_ms`, `description`. Сохраняет создание проекта, включение или выключение учёта оплаты и добавление тарифа. События входят в резервную копию и видны на экране истории проекта.

## Правила

- Конец плана должен быть позже начала. Для завершённой смены учтённый конец должен быть позже начала; перерыв не может превышать длительность смены.
- Для проекта без оплаты тариф не требуется. При включённой оплате тариф обязателен для нового check-in и должен принадлежать проекту смены.
- Отчёты и CSV вычисляются из текущих исправленных значений смены; история хранит исходные и предыдущие значения.
- При открытии старой базы версия 4 назначает Row ID существующим сменам и переводит `armed` в `active`, сохраняя проекты, смены и события.
- Резервная копия данных имеет формат версии 4. Импорт принимает также копии версий 1–3, проверяет связи и заменяет данные в транзакции. Новые файлы зашифрованы паролем; старые незашифрованные файлы принимаются для переноса.

## Дальнейшее развитие

Смена тарифа внутри одной смены, отдельные интервалы перерывов, заметки и автоматическая синхронизация пока не входят в текущую схему. Для них понадобятся отдельные миграции и правила расчёта.
